Why you can't just upload it the challenge

Not a Claude limit. Not a Copilot limit. A physics limit.

Context window

The ceiling

Frontier models top out at 200K–1M tokens. One XAF year alone consumes 600K–900K. Four years never co-exist in any single prompt — on any platform.

Signal-to-noise

The attention tax

Even with headroom, 99K routine postings drown out the 50 lines that matter. Anomalies disappear into the mass.

Cost & latency

The running cost

A full-file prompt would run to tens of euros and minutes per turn. Not viable for interactive auditor work.

XML verbosity

The tax on format

XAF is tag-heavy — <trLine>, <amnt>, <desc>. A good 60–70% of the bytes are structure, not analytic content.

The conclusion isn't "use a bigger model." It's pre-filter the data before the model ever sees it — and that's what the rest of this discussion is about.

Speaker note · kill the "but what if we used GPT-X" question early Expect someone to ask whether a bigger-window model solves it. Answer directly: even with a 1M-token model, you'd still burn €15–€30 per run, wait three minutes, and get a worse answer than a preprocessed one. The bottleneck is relevance, not capacity.

Second likely question: "Can't we just convert it to CSV first?" That is preprocessing — we'll formalise that in the pipeline slide. It's the right instinct.
The pipeline, end to end architecture

Five stages. Each one does less than the one before.

Auditor drops the XAFs into SharePoint. Logic Apps triggers the Azure Function. The Function parses the XML with streaming iterparse, writes six small CSV/JSON artifacts. Copilot Studio picks those up and produces the report — saved back into the same client folder.

Speaker note · walk the arrows once, slowly The reduction story is the headline: 3.4 million XML lines in, ~few hundred KB of relevant rows out. Everything downstream is operating on data that already fits in any model's context window, so we get to choose the model for quality, not capacity.

Logic Apps is drawn dashed because it's the thinnest piece — it's the glue, not the value. If Crowe prefers Power Automate as the trigger, that's fine; the Function does the real work either way.
Preprocessing — four options in the Microsoft stack architecture

Low-code is tempting. 88 MB of XML isn't low-code.

OptionBest whenWatch-out
Azure Function · Python
Our pick		 Streaming XML parse with lxml.iterparse · custom filter logic · fastest to build · full control Developer-owned repo · not low-code · Crowe Technology needs to host or inherit it
Power Automate + custom connector Business users want a no-code trigger and flow Struggles at 88 MB XML — real risk of timeouts and memory limits
Azure Data Factory This becomes a repeatable ETL across many clients Heavier setup · XAF parsing still needs a custom activity underneath
Logic Apps (orchestrator only) Coordinating trigger, Function, and notifications Not the parser itself — delegates to the Function

Honest recommendation: Azure Function in Python, orchestrated by Logic Apps. Start small. Graduate to ADF only if and when this becomes a multi-client pipeline.

Speaker note · where the honest conversation happens Don't dress up Power Automate. It will time out on an 88 MB file. If Crowe's IT pushes hard for it anyway, the compromise is: Power Automate as the trigger, which then calls an Azure Function to do the actual parse. That's a perfectly fine pattern — it just means accepting that "no-code" ends at the flow definition, not at the parser.

If they ask about Fabric / Synapse — same answer as ADF. Heavier than we need for one client; worth the setup when we're serving ten.
What the Function extracts architecture

Six filters. Six small artifacts the agent can actually read.

manual_entries.csv

Every posting with journal type "Memoriaal" and a non-empty narrative. Where humans intervened — almost always where the interesting questions live.

large_transactions.csv

Lines with |amount| > threshold. Threshold configurable — EUR 5K or 10K, depending on Crowe's materiality rule.

period_13_entries.csv

Closing-period postings: accruals, year-end cut-off, management overlays. Favourite habitat of earnings management.

balance_by_account_yoy.csv

Debit/credit aggregated per GL code per year across all four files. The trend table — where real DD value lives.

flagged_accounts.csv

Lines whose GL code matches a watch-list: management fees, related-party, intercompany, loans to shareholders. Needs the code map from Crowe.

metadata.json

Row counts, totals, file hash. Reproducibility and an audit trail the auditors can keep in the working paper.

Rough reduction: 3.4 million XML lines → a few hundred KB of rows. Comfortably inside any model's window, and most of it actually relevant.

Speaker note · this is where Crowe's tacit knowledge lives The filters are deliberately plain. The parameters — which GL codes count as related-party, which journals count as manual, which amount is material for this deal — are where Crowe's expertise has to come in. We can't guess that; Bram and Marieke have to hand us the list.

Ask directly: "Do you have a standard normalization checklist today? Even an internal slide deck or template works." If yes, that's week-zero input. If no — that's a conversation to have before the pilot starts.
The agent, in shape architecture

One agent, three topics, one prompt per topic.

The Copilot Studio agent receives the filtered CSVs and runs one of three skills: anomaly detection, normalization suggestions, year-over-year trend analysis. Each skill is a named prompt — here's the anomaly skill in Dutch, production-shape.

What lands on the auditor's desk architecture

Two files, one folder, existing format.

Word

DD memo · narrative

One-pager plus annexes. Flagged items grouped by theme, the three highest-priority normalization candidates with reasoning, YoY highlights. Drops into the existing DD working-paper template.

Excel

Working paper · line-by-line

Every flagged line with columns for Auditor decision (Accept / Reject / Follow up) and Normalization amount. This is the document auditors already use — we just pre-fill it.

Both files land back in the same SharePoint client folder as the source XAFs. No new tool. No new portal. The engagement team sees the output where they already look.

Speaker note · the integration story is the adoption story Auditors won't log into a new app. Output has to show up where they already work — SharePoint, Teams, the existing working-paper template. This is the difference between a demo that wins the room today and a tool that's still running in Q4.

Ask Bram and Marieke to share the actual DD working-paper template. That's the one asset that turns this from "prototype" into "drop-in."
Who owns it · how it plugs in the discussion

Managed service now, Crowe-owned later.

Ownership path

Phase 1 · Tatoma managed service. Crowe uploads files; we return the artifacts and run the agent. Fast to stand up, validates the value.

Phase 2 · Crowe Technology owns it. Repo + runbook handover. Function and filters live in a Crowe-managed Azure subscription.

Integration with existing workflow

Trigger: SharePoint client folder (already used). Output: same folder, existing Word/Excel templates. Questions from the agent: reachable in Teams, so auditors stay in their chat client.
One-off for Faraday? Or · repeatable pipeline across every XAF 3.2 client

XAF 3.2 is a Belastingdienst-mandated Dutch standard — Exact Online, AFAS, Twinfield all produce it. Built once, the pipeline compounds across every Crowe M&A engagement from this one forward.

Speaker note · the ownership decision is the commercial decision Managed service is easier to start; Crowe-owned is where the long-term value sits. Explicitly frame the two phases so no one in the room feels locked into either one.

Probe: does Crowe Technology have Python / Azure Function skills today, or is that a hire / upskill path? Answer shapes how quickly we can migrate out of Phase 1.

The reusability point at the bottom is the real business case. Say it out loud: "You build this with us once, on Faraday. Next Exact client, the same Function runs — nothing new to write."
MVP timeline the discussion

Six to eight weeks. Three weeks of build, the rest is validation.

Week 0 Workshop output — filter shortlist, thresholds, GL code map confirmed with Bram. Normalization checklist requested. in-session
Weeks 1–2 Azure Function v1 parsing one XAF year. Produces manual_entries, large_transactions, balance_by_account_yoy. ~1 dev-week
Week 3 Copilot Studio agent v1 · three topics · tested end-to-end against KleurRijker 2024. ~3 dev-days
Week 4 Output templates (Word + Excel), Logic Apps orchestrator, SharePoint trigger wired up. ~3 dev-days
Weeks 5–6 Internal pilot on Project Faraday — auditors use it live, feedback loop, prompt tuning. validation
Weeks 7–8 Harden for a second client. Add period_13 + flagged_accounts filters. Handover docs. ~1 dev-week

Realistic only if Week 0 delivers the normalization checklist and GL code map. Without them, everything slips a fortnight.

Speaker note · set expectations honestly Three dev-weeks of build, three of validation. That's the shape of a good audit-tech pilot — not a two-week hackathon.

The critical-path dependency is Crowe's input in Week 0: the normalization checklist and the GL code map. If those don't materialise, Weeks 1–2 start with us guessing, which burns the pilot's credibility. Flag it explicitly.
Quality & reuse signals the discussion

How would you know this worked, six months in?

Quality signals — what makes one run "good"?

  • Of the lines the agent flags, what share does the auditor accept as worth a follow-up?
  • Are the false negatives the ones that would have embarrassed the engagement team?
  • Does the normalization memo need heavy editing before the partner signs off, or light?

Reuse signals — does the pipeline stick?

  • What share of M&A engagements with XAF availability run through it per quarter?
  • How many hours per engagement does it save — analyst, manager, partner?
  • Who's asking for it outside M&A — audit, tax, advisory?
Speaker note · quiet part of the session Don't steer. Bram and Marieke know what "worth it" looks like in their practice — we don't. Write whatever they say on the canvas verbatim.

If someone volunteers a number — "if it saves two days per engagement I'd run it on every deal" — write that down. That's the success metric that survives the workshop.

If nobody volunteers numbers, the fallback ask is: "pick one quality metric and one reuse metric we should measure after the pilot." That's enough to move forward.
